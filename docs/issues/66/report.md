- **R1-C1 — Medium:** The shared validation/error contract needs an explicit unsupported-operation result and composition with #84's descriptor classifier. Evidence: docs/issues/66/design.md:58-64 validates operation/flags but defines only Invalid, Io and Stopped, with Invalid -> EINVAL and every other result -> EIO; it then says unsupported mappings are frozen. Current ublk.rs:1279-1281 and :1454-1456 returns EOPNOTSUPP for unsupported operations, which none of those shared errors can represent. #84 design.md:43-63 explicitly selects one descriptor classifier used by both modes, with registration-first EIO, unsupported flags/operations EOPNOTSUPP, and invalid read/write ranges EINVAL. #66 currently mentions #84 only for flush/discard behavior (:88-90), so its proposed universal validation contract is incomplete at the precise error distinction S2 requires.
- **R1-C2 — Medium:** Fresh request bindings must be explicitly separate from the preserved device lifetime and the endpoint states used by #48. Evidence: docs/issues/66/design.md:29-32 gives a registry entry a current-process Binding and Endpoint::Ublk{id,dev_t,held_fd}; :46-47 requires a successor's fresh binding, but :155-158 leaves kept/device-less states to later reconciliation. #15 device-lifetime-contract.md requires the full (volume,first_epoch,boot_uuid,instance,generation,rdev,diskseq) identity in device-info and conditional detach. #48 design.md:289-312 requires that exact original device tuple survive recovery while routing separately uses a new generation; kept entries have no held fd. A new Binding cannot supply that original tuple, and the proposed held-fd endpoint shape does not represent a kept device. The plan promises unchanged typed status/control behavior without spelling out these two distinct identities or a representable kept state.
- **R1-C3 — Nit:** The Open questions introduction still says the approved timing and test-only choices are unaccepted. Evidence: docs/issues/66/spec.md:81-82 says neither 'after #15' nor 'test-only' is recorded as accepted here, immediately before :85-87 records both as settled; decisions.md:14-25 preserves their approval.
- **SEC66-R1-01 — Medium:** Bounded routing needs an event-capacity and terminal-delivery rule that remains nonblocking under the engine lock. Evidence: docs/issues/66/design.md:41–45 sends bounded events and removes the route at a terminal event; :98–100 derives queue capacities from queues×depth without specifying event slots or full/closed handling. The retained #15 router contract (design.md, The router, lines31–37) routes under the engine lock through nonblocking try_send. Current ublk.rs:605–615 ignores try_send failure and removes the waiter for Done. One legitimate depth-one read crossing two remote chunk pieces can generate Piece, Piece, Done before its consumer runs (engine.rs:1889–1900 emits each direct-read Piece; sub_done then emits Done). A request-count bound alone is not an event bound. Converting these channels to bounded queues without a stated mailbox/credit policy can discard Done after route removal, hang the request and exhaust the binding; blocking on capacity while holding the engine lock can deadlock the read/stop path.
- **SEC66-R1-02 — Medium:** The frontend batch lifetime contract does not define how unwinding is stopped before pending kernel buffers are destroyed. Evidence: spec.md S5 promises safety on unwind, while design.md:73–84 says batches retain ownership and invokes an existing daemon fail-stop path if draining is impossible, but does not define an armed unwind/drop guard or its destruction order. Current local_read and fast_read_copy in ublk.rs:1293–1341,1638–1694 publish raw-buffer SQEs while building pending Vecs. Pinned libublk0.4.8 io.rs:2231–2233 unwraps submission, uring_async.rs:546–570 eagerly pushes SQEs before returning the future, and UblkUringOpFuture (uring_async.rs:26–90) has no draining Drop. Ordinary future/Vec ownership therefore does not keep a request buffer alive when its task unwinds or is dropped with SQEs outstanding. #85 explicitly adds armed abort-on-unwind protection to UringDevice; that separate device ring does not protect the ublk queue ring, and the current flaminio-io daemon has no existing abort/exit path to invoke here.
