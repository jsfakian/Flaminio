## Findings
1. Low. `done()` counting only a *running* device entry silently departs from #15, and the doc says it matches it. design.md:222-227 cites "#15's 'its retry stops once that volume has an entry'" (#15 design.md:71, :726, tested there) and then says "as today's check does". Today's `attached` (ublk.rs:752, set at :1044) is a running-device flag, but #15 replaces it with "has an entry" (any state). The new rule also excludes starting and stopping entries of the volume, which the previous round counted (item 86 "a device entry"). decisions.md item 90 says it "refines" 86, which is honest, but #17 now contradicts #15's own test (#15 :726) without saying so; if both land, one of the two tests fails. The behaviour is defensible (a starting attach may fail) and the cost is bounded: extra refused attempts every 5 s up to STARTUP_ATTACH_LIMIT. Fix: state that #17 changes #15's rule from "any entry" to "a running entry", name #15's test it replaces (or coordinate that #15's text change), and say how "running" is read (the entry's state in the registry, not the `Attached` mutex, which #15/item 86 retire). Add a test: a starting entry of another client (its attach held unanswered) does not end the retry, and the retry ends once that entry runs.
2. Low. The concurrent test's refusal text depends on the winner's entry still being `starting`. If the fake attach completes before the loser reserves, the answer is `error: VOLUME is running here`, not `... is starting here`. The test must hold the winner's metadata phase unanswered until the loser's reserve is refused, then release it; the design says only "once the winner's entry is reserved". Same hold is needed for "socket first ... the socket client's device then running" (device must run before the startup retry's `done()` after the interval; say the test releases it before advancing the interval).
3. Low. The gate position relative to the `done()` re-check is unspecified: "after each runner's wait, before its reserve" (design.md test text) vs startup_attempt's order "wait, done(), reserve" (design.md:234-239). If the gate is before `done()`, the startup runner's check runs after the winner's entry exists (harmless, a starting entry is not counted by finding 1, but a running one is: the startup runner would stop without reserving, and the test would not see the refusal). Fix: put the gate between `done()` and the reserve, and say so.

## Security
No new finding. The gate and waiter count are cfg(test) only; the refusal reveals nothing new; the retry stays bounded by STARTUP_ATTACH_LIMIT and the 30-s wait. Counting only running entries cannot let a stale party hold the retry open beyond the 5-minute limit.
