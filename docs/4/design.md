# Issue #4: run every fuzz target for 10 minutes clean — design

## The fuzz crate becomes a library with thin targets

`dataplane/fuzz/src/lib.rs` gets one public function per target, holding the body that is in
`fuzz_targets/<target>.rs` today, unchanged:

```rust
pub fn superblock(data: &[u8]) { ... }
pub fn metadata_pages(data: &[u8]) { ... }
pub fn journal(data: &[u8]) { ... }
pub fn repl_frame(data: &[u8]) { ... }
pub fn capability_token(data: &[u8]) { ... }
```

Each `fuzz_targets/<target>.rs` shrinks to
`fuzz_target!(|data: &[u8]| flaminio_fuzz::<target>(data));`.

**Rule:** `lib.rs` never refers to `libfuzzer_sys`. The dependency is optional, behind a
`fuzzing` feature that every `[[bin]]` requires (`required-features`). It is a default feature, so
every cargo-fuzz command (`run`, `tmin`, `cmin`, `coverage`) works as usual; the regression test
turns it off (`--no-default-features`) and so builds no libFuzzer and no C++ at all. Only fuzzing
and `make lint`, which compiles the binaries, need the C++17 compiler of its build script
(`build-essential` on the runners, Xcode's tools on macOS).

## The regression test

A unit test module in `src/lib.rs`, run with `cargo test --lib --no-default-features` in
`dataplane/fuzz`
(`--lib` only skips doc-tests; the binaries are not built by `cargo test` either way, as they
have `test = false` and there is no `tests/` directory):

- `TARGETS: &[(&str, fn(&[u8]))]` lists the five harnesses, generated by a macro from the
  function names (`stringify!`), so a name cannot be paired with another target's function. The
  set check also reads each `fuzz_targets/<t>.rs` and requires it to call `flaminio_fuzz::<t>(`.
- **The set check (S6):** the names in `TARGETS`, the `name` of every `[[bin]]` in `Cargo.toml`
  (parsed with the `toml` crate, a dev-dependency of the fuzz crate), the file stems of
  `fuzz_targets/*.rs` and the directory names under `regressions/` must be equal. Paths come from
  `CARGO_MANIFEST_DIR`; a name that is not UTF-8 is kept lossily, so it shows as a mismatch.
- **The replay (S4):** for each target, the entries of `regressions/<name>/` in sorted order.
  An entry that is not a file named as in S3 fails the test, naming it, and is not replayed. For
  each file:
  - the path is written with `std::io::stderr().write_all`, which libtest does not capture, so an
    abort still leaves it in the log;
  - the harness runs on a thread spawned with a 2 MiB stack, inside `catch_unwind`; the result
    comes back through a channel;
  - waiting longer than 5 seconds records a timeout and ends the replay: the remaining
    inputs are listed as not run. The stuck thread is left behind until the test process exits,
    so at most one is ever spinning;
  - a panic records the file.

  The test fails at the end, listing every failed file, so one run shows everything a change
  broke.

## Seeding the fuzzer

`scripts/dev/fuzz.sh`:
- takes its targets from `cargo fuzz list` (the `[[bin]]` entries, which the set check keeps in
  step with the rest) instead of a hard-coded list, and stops if that list is empty: a failing
  `cargo fuzz list` inside `mapfile` is invisible to `set -e`;
- reads that list with a `while read` loop, not `mapfile`, which macOS's bash 3.2 lacks;
- runs them all, and exits with an error at the end listing those that failed;
- creates `corpus/<target>` itself: cargo-fuzz only creates it when it chooses the corpus, and
  libFuzzer refuses a corpus directory that does not exist;
- runs `cargo fuzz run <target> corpus/<target> regressions/<target> -- -max_total_time=<s>
  -timeout=10`: libFuzzer's default timeout is 1 200 seconds, which would let a 10-minute hang
  pass as a slow input.
  libFuzzer writes new inputs only to the first directory and never deletes seed files, so the
  committed regression inputs are left as they are.

## Fuzz workflow

The workflow runs one at a time (`concurrency: fuzz`, not cancelling a run in progress): runs
share the corpus on the runner host and the fuzz issue. The dispatch input `seconds` is a choice
of 60, 300 or 600, which keeps five targets and their builds within the job's 120 minutes
(GitHub's expressions have no arithmetic to derive the limit from the input).

The `fuzz` job, on failure, and also when it is cancelled at its time limit:
- copies `dataplane/fuzz/artifacts/` to `~/.cache/flaminio-ci/fuzz-artifacts/<run id>-<attempt>/`
  on the runner when it holds any file, from a step that runs with `if: failure() || cancelled()`;
- then uploads it as the artifact `fuzz-artifacts-<attempt>` (`retention-days: 90`). A re-run is
  a new attempt of the same run, and an artifact name can be used once per run.

A second job, `report`, needs `fuzz` and runs with
`if: always() && (needs.fuzz.result == 'failure' || needs.fuzz.result == 'cancelled')`: after any
failure or cancellation, with or without inputs, so a hang stopped at the time limit is reported
too. Without `always()`, GitHub would add `success()` to the condition and the job would never run
after a failed `fuzz`. Whether the attempt kept inputs, it asks the API for the run's artifacts
and looks for this attempt's `fuzz-artifacts-<attempt>` (the list holds every attempt's), not a
job output, which a job cancelled at its time limit may not pass on. It also finds the fuzz job
of this attempt, by name, through the same API (the step fails unless exactly one job has that
name, rather than report nothing after a rename): if it ran no step, no runner took it, centaur's
runners are probably down, and the note says so. That is the case running the report on GitHub's
runners is for. A run cancelled while still queued by a newer one (the concurrency group) runs no
job at all, the report included.

It runs on a GitHub-hosted runner (`ubuntu-latest`), not centaur: a run that failed because
centaur hung or lost its runners must still be reported. It only calls the API, for about a
minute, when a run failed, so it costs next to nothing of the Actions minutes. It has
`issues: write` and `actions: read` and nothing else, checks nothing out, and sets two variables
for `gh`: `GH_TOKEN` to the workflow's token, and `GH_REPO` to `github.repository`, which `gh`
cannot read from a checkout it does not have. It:
- creates the `fuzz` label only if it is missing, so it never resets what maintainers changed;
- comments on the open issue labelled `fuzz` if there is one, or opens "Fuzz run failed",
  labelled `fuzz`, linking the run. The note says whether the run kept failing inputs (and where),
  or ended without any: a build or toolchain failure, or a hang, would otherwise skip the weekly
  fuzzing without anyone noticing.

Keeping it a separate job keeps `issues: write` away from the steps that build and run code.

## Make, lint and CI

- `dataplane/fuzz/Cargo.toml` (the root of its own workspace) gets `[profile.dev] opt-level = 3`:
  the replay then runs optimized, as the fuzzer's code is, with the debug assertions and overflow
  checks a dev build keeps. It is still faster than the fuzzer, which adds instrumentation, hence
  the replay's stricter limits (S4). cargo-fuzz's own builds (release) are unaffected.

- `make fuzz-regressions`: `cd dataplane/fuzz && cargo test $(LOCKED) --lib
  --no-default-features`. CI passes `LOCKED=--locked`, so it replays exactly what the lockfile
  pins; locally it is empty, so a developer adding a dependency sees the replay run, not a
  lockfile error. Dependabot watches the fuzz crate's lockfile too (`/dataplane/fuzz`).
- The set check also requires `required-features = ["fuzzing"]` on every `[[bin]]`, without which
  a plain `cargo build` of the crate fails.
- `make test` runs it after the data plane's and the Go tests.
- `make lint` adds `cargo clippy $(LOCKED) --all-targets --all-features -- -D warnings` and
  `cargo fmt --check` in `dataplane/fuzz`. Clippy builds the five binaries too; they build on
  stable. CI passes `LOCKED=--locked`, as for the replay.
- The fuzz job prunes copies of failing inputs older than 90 days from the runner host, as GitHub
  does with the artifacts.
- A Dependabot pull request for `/dataplane` that changes a dependency the fuzz crate shares
  (through `flaminio-format` or `flaminio-net`) leaves the fuzz lockfile stale, and the contracts
  and Rust test jobs fail; Dependabot cannot update the second lockfile in the same pull request.
  The fix is one command on that branch, in `docs/ci.md`.
- CI's Rust test job runs `make fuzz-regressions` after `cargo test --locked` in `dataplane`.
  `CARGO_TARGET_DIR` (from the setup action) applies to the fuzz crate as well: its builds share
  the runner's persistent target directory, which is harmless.
- `docs/ci.md` gets the S7 procedure, and the table row of the Rust test job.

## Verifying S1

A Fuzz run with 600 seconds per target, dispatched on `main`. If it reports failing inputs, they
go into `regressions/` and get fixed in this issue's pull request; the issue closes on the first
clean run on `main` after it is merged.

## Decisions

- **Harness functions in the fuzz crate, not in the crates under test.** The harnesses build
  their inputs (repairing a CRC, choosing a page type) in ways that serve fuzzing only; keeping
  them next to the targets keeps the product crates free of fuzz code. *Rejected:* replaying
  regressions from `flaminio-format`'s and `flaminio-net`'s own tests, which would duplicate each
  harness.
- **A unit test in the library, not an integration test.** An integration test would make
  `cargo test` build and link the five binaries every time, for nothing.
- **Four registrations per target, checked, not generated.** A target is listed in `TARGETS`, in
  `Cargo.toml`, in `fuzz_targets/` and in `regressions/`. The set check fails, naming the
  mismatch, when one is missing. *Rejected:* a macro or build script generating some of them,
  which would add moving parts to save one line per target, for something done rarely.
- **The fuzzer keeps cargo-fuzz's default build: optimized, with debug assertions.** cargo-fuzz
  adds `-Cdebug-assertions` (which also turns on overflow checks) unless `--release` (`-O`) is
  given (`project.rs` of cargo-fuzz 0.13.2), so the fuzzer already enforces what the replay's dev
  profile does. *Rejected:* passing `-a` explicitly, which changes nothing.
- **The replay builds every dependency optimized** (`[profile.dev] opt-level = 3`), not only the
  crates under test: the token harness's time is mostly its signature checks in the crypto
  dependencies, and the runners keep their build directories, so the cost is paid once per
  dependency change. *Rejected:* per-package profiles, which would skew the replay's timing.
- **A fresh zeroed image per journal input.** Reusing one image and clearing what the previous
  input wrote saves an allocation, but rests on an invariant (an input writes only inside its own
  length) that a later change to the harness could break silently, leaking one input into the
  next. A zeroed allocation is cheap: the pages it does not touch are never written.
- **Eight selector slots, two free.** A quarter of `metadata_pages` inputs do nothing, the price
  of a first byte whose meaning never changes as decoders are added, up to eight; a ninth would
  need a wider table, remapping the inputs once. Moving from the old `% 6` remapped the corpus
  kept on the runner once too; the fuzzer rebuilds it. *Rejected:* `selector % <number of
  decoders>`, which reroutes every committed input whenever one is added; and returning
  libFuzzer's `Corpus::Reject` for the free slots, which would make one harness return a value
  the others do not, and the target binary depend on it, to save a share of one target's time.
- **Linting compiles the binaries,** so `make lint` needs the C++ compiler that fuzzing needs
  anyway. *Rejected:* linting the library alone, which would leave a binary that no longer builds
  to be found by the weekly run.
- **Memory and leak limits stay with the fuzzer** (S5). Enforcing them in the stable test would
  need a counting global allocator and LeakSanitizer; the weekly run replays every regression
  input with them anyway, so a committed `oom-` or `leak-` input whose fix regresses is caught
  within a week, and reported.
- **Crashes are added by hand** (S7), not by the workflow: a failing input needs a fix in the
  same pull request, which an automatic commit cannot provide. The workflow makes sure nobody
  misses one.

## Risks

- A harness that fails on purpose (the `assert_eq!` in `repl_frame`) reports that as a failure in
  the regression test too. That is intended: the assertion is the property being fuzzed.
- A hung input leaves one thread spinning until the test process exits; the replay stops at the
  first timeout, so there is never more than one.
